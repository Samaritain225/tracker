# How this project works

## Running it on an Android emulator

The emulator on this Apple Silicon Mac is `arm64-v8a`, not x86. Building with
`./gradlew assembleDebug -PreactNativeArchitectures=x86_64` produces an APK that
installs successfully and then crashes on launch with a missing-native-library
error that looks nothing like an architecture problem. Always pass
`-PreactNativeArchitectures=arm64-v8a`. Check with `adb shell getprop
ro.product.cpu.abi` against `unzip -l app-debug.apk | grep lib/` when a fresh
install misbehaves.

`npx expo run:android` blocks for longer than ten minutes because it builds and
then holds the dev server in the foreground. Build with gradlew directly and run
Metro separately instead, or the command gets killed partway and leaves a
half-correct APK behind.

Run `adb reverse tcp:8081 tcp:8081` before launching, or the deep link below
fails with `ConnectException: Failed to connect to localhost/127.0.0.1:8081` on
a red error screen. Inside the emulator `localhost` is the emulator, not the
Mac. `npx expo run:android` sets this up for you, which is why the failure only
shows up when driving gradlew and adb by hand.

After a fresh install the dev client does not auto-connect to Metro — it sits on
`DevLauncherActivity` and looks like a hang. Deep-link past it:
`adb shell am start -a android.intent.action.VIEW -d
"tracker://expo-development-client/?url=http%3A%2F%2Flocalhost%3A8081"`.

`expo prebuild` does not write `android/local.properties`, so a gradlew build
straight after one dies with "SDK location not found" even though the SDK is
installed. Recreate it with `echo "sdk.dir=$HOME/Library/Android/sdk" >
android/local.properties`. The whole `android/` tree is gitignored, so this is
lost on every prebuild rather than once.

The emulator and Metro die together. If the emulator drops, restart Metro too —
a live `expo start` process with a dead device produces confusing "app not
running" results rather than an obvious error.

To test that an upgrade keeps existing data, install the old build first, then
the new one over it with `adb install -r`. A debug build has no JavaScript inside
it and loads it from Metro, so the old build needs the old code serving it: check
the old commit out in a `git worktree`, `npm ci` there, and run Metro from it.
Both debug builds are signed with the template's debug key, so the second install
is a real upgrade (`firstInstallTime` stays put in `dumpsys package`). Seed data
by copying `files/SQLite/cycle.db` out with `adb exec-out run-as
com.doumbia225.tracker cat`, editing it with `sqlite3`, and copying it back.

To edit the database on the emulator, stop the app first, copy out both
`cycle.db` and `cycle.db-wal`, run `PRAGMA wal_checkpoint(TRUNCATE)` before the
edit, and delete `cycle.db-wal` and `cycle.db-shm` on the device when copying
it back. Recent writes live in the WAL file; skip any step and the edit is
either missing data or silently overwritten on the next launch.

Expo's floating dev-tools button sits over the top right of every debug screen
(around 970,245 on Lumi_API35), so a tap on a switch or button there opens the
dev menu instead. Close the menu with its X and scroll the control lower before
tapping it, or the test silently checks nothing.

Do not run `npx expo lint`: the project has no ESLint, so it rewrites
`package.json` and `package-lock.json` and adds `eslint.config.js`, then fails.

Maven Central keeps cutting off the download of `react-android-<version>-debug.aar`
(about 290 MB), and Gradle fails with "Connection reset" however many retries it
is given. Fetch it with `curl -C - --retry 5` instead, check it against the
`.sha1` file next to it on Maven, and put it in
`~/.gradle/caches/modules-2/files-2.1/com.facebook.react/react-android/<version>/<sha1>/`.
Gradle then uses that copy instead of downloading.

This Mac's disk is nearly full, and a clean Android build needs about 5 GB free.
Check `df -h ~` before starting one: when the disk fills mid-build, Gradle fails
and then no shell command can run at all until space is freed.

## Native configuration

`android/` is gitignored and regenerated by `expo prebuild`. Every native config
change (permissions, plugins, manifest entries) belongs in `app.json`; editing
`android/app/src/main/AndroidManifest.xml` directly works until the next prebuild
silently discards it. A change there needs a prebuild plus a native rebuild to
reach the device, not just a JS reload.

## Privacy posture

The app lock is scoped to keeping someone who picks up an unlocked phone out of
the app, and nothing more. It is not meant to survive someone having real access
to the device. The full reasoning and the three consequences that follow live in
the header of `src/providers/app-lock-provider.tsx` — read it before changing
anything about locking, biometrics, or screenshots.

Three properties look like bugs and are decisions: the lock cannot blank the
OS app-switcher snapshot (it is a React overlay, not FLAG_SECURE), there is no
PIN fallback, and the SQLite file is plaintext on disk. Raising any one of them
without the others buys very little, so treat it as one scope change rather than
three fixes.

`android.allowBackup` is false in `app.json` and must stay that way. The database
is unencrypted, so with backup enabled a user's full cycle history is uploaded to
Google Drive and restored onto any device signed into that account — which
contradicts the one thing the app promises.

## Platform gotchas

On Android a `<Text selectable>` ignores `numberOfLines`, so the text wraps and
gets clipped by its container instead of truncating. The tell is one Text in a
card ellipsizing correctly while its neighbour does not.

## Dependencies

Regenerate or update `package-lock.json` with npm 11 (`npx -y npm@11 install`),
not the npm 12 installed on this Mac. EAS installs with the npm that ships with
the Node version pinned in `eas.json`, and an earlier lockfile it disagreed with
failed every cloud build at "Install dependencies". Check with `npx -y npm@11 ci
--dry-run` before pushing.

## Conventions

Commits are conventional, scoped, imperative, and describe user-visible impact
rather than the mechanism: `fix(home): stop "days until" going stale`. One
concern per commit.

Database mutators on the hooks swallow their own errors into `error` state
rather than throwing, so every one of them returns its outcome — a boolean, or
the new row's id — never `void`. A mutator that resolves void cannot be
distinguished from a successful one by an awaiting caller, which is exactly how
day-details used to show a green success tick over a discarded entry. Match this
when adding a mutator.

Never write a bare `db.delete(table)` with no `where`. SQLite's truncate
optimisation then skips the change notifications `useLiveQuery` listens for, so
the rows vanish from the database while every screen keeps showing them. Add an
always-true condition such as `where(isNotNull(table.id))`; `deleteAllData` in
`src/services/user-data.ts` does this.

A form whose starting values come from a live query must wait for that query
before it mounts: render a loading screen, then the form, as `day/[date].tsx`
and `pregnancy/setup.tsx` do. `useState` keeps whatever it saw on the first
render, and on the first render every live query is still an empty list — the
pregnancy setup prefilled "28 days ago" instead of the latest period that way.

SQLite foreign keys are off in expo-sqlite, so the `ON DELETE CASCADE` on
`pregnancy_visits` and `pregnancy_moments` does nothing. Code that deletes a
pregnancy must delete its visits and moments itself, as `removePregnancy` and
`deleteAllData` do; otherwise they survive as orphans and reappear in backups.

The app's mode (cycle, pregnant, recovery) is derived from data by
`resolveMode` in `src/utils/pregnancy.ts` and never stored. Recovery covers a
loss as well as a birth: until a period is logged after the pregnancy ended, the
latest period on record is from before it, and treating that as a normal cycle
shows "90 days late" and the "I'm pregnant" prompt to someone who has just had a
loss.

Cycle maths lives in `src/utils/` as pure functions with no database access, and
is the only part of the app under test (`npx jest`). Screens and hooks
delegate to it so Home and Insights can never disagree — `computeCycleLength` is
the single source of truth for average cycle length, and `computePeriodDuration`
for how long a given period ran.

Name every symptom through `labelOf` from `useCustomSymptoms`, or
`symptomLabel` in `src/utils/symptoms.ts` for pure code, never through
`t(\`day_details.symptom_${key}\`)` directly. Symptoms she adds herself are
stored in logs as `custom:<id>`, so a direct translation lookup shows her a raw
id. Never delete a `custom_symptoms` row either: past logs still point at it,
which is why "My symptoms" only hides one.

Adding a package with native code (as `expo-print` was in stage 6) means
rebuilding the debug app with Gradle before testing. Metro bundles the
JavaScript fine either way, but the old debug build has no native half of the
module, so the screen that uses it fails only when it runs.
