# How this project works

## Running it on an Android emulator

The emulator on this Apple Silicon Mac is `arm64-v8a`, not x86. Building with
`./gradlew assembleDebug -PreactNativeArchitectures=x86_64` produces an APK that
installs successfully and then crashes on launch with a missing-native-library
error that looks nothing like an architecture problem. Always pass
`-PreactNativeArchitectures=arm64-v8a`. Check with `adb shell getprop
ro.product.cpu.abi` against `unzip -l app-debug.apk | grep lib/` when a fresh
install misbehaves.

`npx expo run:android` blocks for longer than ten minutes because it builds and
then holds the dev server in the foreground. Build with gradlew directly and run
Metro separately instead, or the command gets killed partway and leaves a
half-correct APK behind.

Run `adb reverse tcp:8081 tcp:8081` before launching, or the deep link below
fails with `ConnectException: Failed to connect to localhost/127.0.0.1:8081` on
a red error screen. Inside the emulator `localhost` is the emulator, not the
Mac. `npx expo run:android` sets this up for you, which is why the failure only
shows up when driving gradlew and adb by hand.

After a fresh install the dev client does not auto-connect to Metro — it sits on
`DevLauncherActivity` and looks like a hang. Deep-link past it:
`adb shell am start -a android.intent.action.VIEW -d
"tracker://expo-development-client/?url=http%3A%2F%2Flocalhost%3A8081"`.

`expo prebuild` does not write `android/local.properties`, so a gradlew build
straight after one dies with "SDK location not found" even though the SDK is
installed. Recreate it with `echo "sdk.dir=$HOME/Library/Android/sdk" >
android/local.properties`. The whole `android/` tree is gitignored, so this is
lost on every prebuild rather than once.

The emulator and Metro die together. If the emulator drops, restart Metro too —
a live `expo start` process with a dead device produces confusing "app not
running" results rather than an obvious error.

## Native configuration

`android/` is gitignored and regenerated by `expo prebuild`. Every native config
change (permissions, plugins, manifest entries) belongs in `app.json`; editing
`android/app/src/main/AndroidManifest.xml` directly works until the next prebuild
silently discards it. A change there needs a prebuild plus a native rebuild to
reach the device, not just a JS reload.

## Privacy posture

The app lock is scoped to keeping someone who picks up an unlocked phone out of
the app, and nothing more. It is not meant to survive someone having real access
to the device. The full reasoning and the three consequences that follow live in
the header of `src/providers/app-lock-provider.tsx` — read it before changing
anything about locking, biometrics, or screenshots.

Three properties look like bugs and are decisions: the lock cannot blank the
OS app-switcher snapshot (it is a React overlay, not FLAG_SECURE), there is no
PIN fallback, and the SQLite file is plaintext on disk. Raising any one of them
without the others buys very little, so treat it as one scope change rather than
three fixes.

`android.allowBackup` is false in `app.json` and must stay that way. The database
is unencrypted, so with backup enabled a user's full cycle history is uploaded to
Google Drive and restored onto any device signed into that account — which
contradicts the one thing the app promises.

## Platform gotchas

On Android a `<Text selectable>` ignores `numberOfLines`, so the text wraps and
gets clipped by its container instead of truncating. The tell is one Text in a
card ellipsizing correctly while its neighbour does not.

## Conventions

Commits are conventional, scoped, imperative, and describe user-visible impact
rather than the mechanism: `fix(home): stop "days until" going stale`. One
concern per commit.

Database mutators on the hooks swallow their own errors into `error` state
rather than throwing, so every one of them returns its outcome — a boolean, or
the new row's id — never `void`. A mutator that resolves void cannot be
distinguished from a successful one by an awaiting caller, which is exactly how
day-details used to show a green success tick over a discarded entry. Match this
when adding a mutator.

Cycle maths lives in `src/utils/` as pure functions with no database access, and
is the only part of the app under test (`npx jest`, 91 tests). Screens and hooks
delegate to it so Home and Insights can never disagree — `computeCycleLength` is
the single source of truth for average cycle length, and `computePeriodDuration`
for how long a given period ran.
